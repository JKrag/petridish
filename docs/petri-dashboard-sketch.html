Two screens, three densities

A rework of the petri TUI, built for the case that actually hurts: eight unattended runs across eight iTerm tabs at 3am, and you want to know which one needs you — without visiting any of them. Then tab for the browser when you do.

The short answer yes

It makes sense, and it costs less than you'd think, because your three densities already map cleanly onto the four buckets the scanner assigns:

Your instinct about tier 2 is structurally guaranteed, not just usually true. _bucket() returns "active" whenever the agent state is working or recent, before it looks at age at all. So an in_flight project can never have a running agent — tier 2 is free to spend that column width on git instead.

The flip side: active also catches anything touched in the last 48h, so tier 1 will contain idle-but-recent projects too. The frames below include one so the card design has to survive it.

The finding that reshapes tier 1

agent.state does not mean what an overnight run needs it to mean. _agent_state_for() is a pure recency clock on the last event:

statemeansduring an unattended run
workinglast event < 90sonly between tool calls
recent90s – 30 minalso: mid-inference, and stalled
idle> 30 minalso: finished, and dead

A delegate-to-local round where Ornith thinks for four minutes reads recent — indistinguishable from a run that wedged four minutes ago. So the dashboard cannot lean on the traffic light. The load-bearing signal is the age of last_event_at, rendered as an elapsed clock, and the ordering principle follows from it: quietest first.

The ordering silence, descending

Sorting tier 1 by most-recent-first puts the healthiest run at the top and buries the wedged one. Inverting it — longest silence first — means the row that needs you is always row one, and a screen you can ignore is one where the top card reads a small number.

Four roomy cards is 16 rows. Eight would be 32 and push in-flight off a 40-row terminal entirely. So the density has to collapse as the fleet grows — same data, one line each:

Two screens tab to switch

Doable, and I think it's the right call — for a reason worth naming. The two screens have different jobs, and that's why one layout serving both ends up serving neither:

  • Screen 1 is an ambient monitor. You leave it open in a pane on a second display and look at it, not with it. Its whole job is answering "anything need me?" from across the room. Interaction is incidental.
  • Screen 2 is a tool you drive. Hands on keys, searching, selecting, opening, resuming. Density beats prominence; every project should be reachable.

The current screen is a screen-2 layout being asked to do screen-1's job. Splitting them lets each stop compromising. tab toggles, z switches density on screen 1, q quits from either.

Why the split pays for itself beyond the layout

Screen 1 has no cursor and no input. That means it's a pure function — render_dashboard(radar, now, width, density) → list[str] — exactly like menubar.py. Which gets you a third consumer for free: a non-interactive swab dash that prints the same block once and exits. Pipe it into a tmux status pane, a cron mail, or a notification. You cannot do that with today's screen, because today's screen is inseparable from curses.

The risk to watch: two renderers drifting into two different idioms for the same fact. Both must build rows from the same tui_state formatters — screen 1 composes them into cards, screen 2 into columns, but neither re-derives "how do we show a dirty branch".

Built what shipped, and what differs from these frames

All of the above is implemented and green under make check. Four things came out differently once the code was real:

  • The keymap footers shrank. These frames advertise ⏎ open and r resume; nothing implements them, so the shipped footers read tab · z · q and tab · j/k · / · esc · q. A footer that promises keys which do nothing teaches you to distrust the whole line.
  • The browser drops the agent column before it truncates. At 100 columns the right pane left ~52 for the table, and blind truncation ate the silence column — the one value the screen exists for. It now sheds whole low-value columns instead, agent first (the detail pane names it anyway), then branch.
  • The stall glyph ignores agent.state entirely. Re-derived from last_event_at at render time, so a projects.json that is two minutes stale can't make the traffic light contradict the counter beside it.
  • Density collapses automatically above four runs, with z as an override — rather than z being the only way.

Verified by driving the real curses TUI through a pty, and by a 36-mutation probe across the new modules: every mutation had to turn a test red. Six initially did not, and each one was a genuine gap — including a header that counted foreign projects it never listed, and a sort key whose explicit grouping turned out to be decorative because a sign was silently doing the work.

What it cost

  • No schema change. Not one new field, not one bucket. group_by_bucket() already returns all four keys in STATUS_BUCKETS order.
  • Variable-height rows are the only real work. The render loop does cursor_y += 1 per project; a three-line card makes that += card_height. move() is unaffected — it flattens to (bucket, index), and one card is still one entry.
  • The detail panel moves to screen 2 and shrinks. Today it reserves 1 + len(detail_lines) rows and format_detail() emits about ten. Screen 1's cards already carry most of that, so the panel belongs only on the browser — and only with the fields a row can't fit.
  • Two screens is a mode flag, not an architecture. One screen variable, one tab branch in the key handler, and two render functions. SelectionState and move() are untouched and belong to screen 2 alone; screen 1 has no cursor.
  • Row budget on 78 × 40. Roomy: 4 cards × 4 = 16, in-flight 4 + 3, stale 3 + 3, chrome 5 ≈ 34. Compact: 8 rows for the same eight runs. That gap is the whole argument for two densities rather than a cap on N — on an overnight fan-out you want to see all of them, not the top three.
  • The silence clock needs a repaint, not just a rescan. The TUI currently redraws on projects.json mtime change. A ticking 47m should re-render on the existing 2s _POLL_MS timeout too — cheap, since the age is derived at render time from last_event_at and needs no new scan.
  • Testable the same way as the rest. The card layout is a pure Project → list[str] function next to format_row() in tui_state.py, snapshot-tested like menubar.py. tui.py stays a thin blitter.
